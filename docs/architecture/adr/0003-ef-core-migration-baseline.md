# ADR 0003: EF Core owns database schema history

Status: Accepted

Date: 2026-08-18

## Context

The production SQLite database predates EF Core migrations. It was created with `EnsureCreated` and
later repaired by ordered handwritten migrations recorded in `__StockTraderMigrations`. Running a
generated EF initial migration directly against that database would try to recreate populated tables.
Continuing the handwritten system would leave the EF model, production schema, and future changes
without one authoritative history.

Production currently records all three compatibility migrations but has no
`__EFMigrationsHistory` table. New installations must not inherit this historical path.

## Decision

EF Core migrations are the sole owner of schema creation and all future schema changes.

- `Data/EfMigrations` contains the initial current schema and model snapshot.
- The repository pins `dotnet-ef` to the same version as the EF runtime through the local tool
  manifest.
- An empty database runs `Database.MigrateAsync` and never creates the legacy history table.
- A database without EF history but with application tables runs the three existing compatibility
  migrations once. It is then compared with the EF relational model table by table, column by
  column, and named index by named index.
- Only a fully compatible legacy database receives the generated initial migration row in
  `__EFMigrationsHistory`. The history-table SQL is generated by EF's provider, not maintained by
  application code. Any later EF migrations then run normally.
- An incomplete legacy database fails startup before EF history is recorded. Existing rows remain
  intact so an operator can repair or restore the database.
- `--verify-ef-baseline` performs the same structural comparison without writing or starting hosted
  services, allowing production volumes to be checked before rollout.

The old `IDatabaseMigration` implementations are compatibility readers only. No new schema change
may be added to that pipeline.

The bridge described here has completed its production adoption and was retired by ADR 0004.

## Consequences

- New and existing installations converge on one EF migration ledger without recreating tables.
- The model snapshot makes schema drift reviewable in source control and detectable in CI.
- Production baseline adoption is deliberately fail-closed and requires a backup before rollout.
- Provider-generated history SQL is used during the one-time bridge; handwritten compatibility SQL
  remains temporarily until every supported legacy database has adopted the EF baseline.
- Deployed health and operations evidence proved the EF history row; ADR 0004 removes the bridge.
